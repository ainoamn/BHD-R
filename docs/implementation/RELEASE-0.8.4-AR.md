# الإصدار 0.8.4 — استرداد مبلغ التأمين بعد المغادرة

**التاريخ:** 2026-10-12
**الصفحات:**

- صفحة الضيف `/[locale]/guest/stays/[bookingId]?ref=…`
- حجوزات العقار `/[locale]/owner/properties/[propertyId]?section=bookings`
- لوحة المالك وجرس التنبيهات (الإجراءات المعلّقة)

## المشكلة

- بعد تأكيد المغادرة لم يكن للضيف طريق لطلب استرداد مبلغ التأمين.
- لم يكن للمالك إجراء متبقٍّ يذكّره بأن الحجز لا يُغلق نهائياً قبل البتّ في التأمين.
- لم يكن هناك مسار للمحاسب لتسجيل التحويل (الحساب أو الهاتف، والبنك، والتاريخ والوقت، والإيصال).
- رحلة الضيف كانت تنتهي بأربع خطوات عند المغادرة، دون أن يعرف مصير تأمينه.

## الحل

### 1. المسار الكامل

```
المغادرة مؤكَّدة (checked_out) ومبلغ التأمين > 0
        │
        ├── الضيف يطلب الاسترداد (اختياري) ── requested
        │
        ▼
المالك أو المدير: اعتماد (بمبلغ ≤ التأمين) ── approved ──► المحاسب يسجّل التحويل ── executed ──► الحجز مغلق (closed)
                  أو رفض بملاحظة إلزامية ── rejected ─────────────────────────────────────────────► الحجز مغلق (closed)
```

- **دون طلب من الضيف:** الإجراء يظهر للمالك تلقائياً كخطوة متبقية لإغلاق الحجز. إن اعتمده المالك يُنشأ الطلب باسمه («طلب من المضيف»).
- **طلب واحد لكل حجز:** مفتاح ثابت `deposit:<bookingId>`، فلا يتكرر الطلب حتى لو ضُغط الزر مرتين.
- **مبلغ التأمين:** من ملف الإقامة للعقار (`stay_profiles.deposit_minor`). الحجز بلا تأمين لا تظهر له هذه الخطوة.

### 2. صفحة الضيف — الخطوة الخامسة

- بعد المغادرة تصير الرحلة **خمس خطوات**: تقديم الطلب ← اعتماد المالك ← الوصول ← المغادرة ← **استرداد التأمين**.
- الخطوة الخامسة هي الحالية حتى يُصرف المبلغ أو يُرفض الطلب، ثم تكتمل.
- **قبل الطلب:** زر «طلب استرداد التأمين» يفتح نموذجاً:
  - طريقة الاستلام: حساب بنكي أو IBAN، أو رقم هاتف (تحويل عبر الهاتف).
  - رقم الحساب أو الهاتف (يُتحقق من صيغته)، والبنك، واسم صاحب الحساب، وملاحظة اختيارية.
- **متتبّع من ثلاث مراحل:** طلب الاسترداد ← موافقة المالك أو رفضه ← تحويل المبلغ، مع التاريخ والوقت لكل مرحلة.
- **الرسائل:**
  - قيد المراجعة: الطلب وصل للمالك.
  - معتمد: المبلغ المعتمد، وهو الآن لدى المحاسب.
  - مرفوض: سبب الرفض كما كتبه المالك.
  - مُحوَّل: المبلغ والبنك والتاريخ، والحساب مخفي إلا آخر 4 أرقام.
- ملاحظة المالك تظهر للضيف (مثل سبب الخصم).
- في «تفاصيل الحجز» صار يظهر «مبلغ التأمين».

### 3. حجوزات العقار — المالك والمحاسب

- **عمود جديد «استرداد التأمين»** في جدول الحجوزات:
  - مبلغ التأمين، وحالة الاسترداد بشارة ملوّنة.
  - طلب الضيف: وقته، وملاحظته، والحساب الذي يريد الاستلام عليه.
  - القرار: المبلغ المعتمد، ومن قرّر، وملاحظته.
  - التحويل: التاريخ، والطريقة، والحساب، والبنك، والمرجع، ومن سجّله، ورابط «إيصال التحويل».
- **حالتان جديدتان للحجز في القائمة:**
  - «بانتظار قرار استرداد التأمين».
  - «بانتظار تحويل التأمين».
  - هذه الحجوزات تظهر أول القائمة.
- **أزرار الإجراء:**
  - «اعتماد استرداد التأمين»: المبلغ (افتراضياً كامل التأمين، ويمكن خصم جزء مع ذكر السبب) وملاحظة اختيارية.
  - «رفض الاسترداد»: ملاحظة الرفض إلزامية (3 أحرف على الأقل)، وتظهر للضيف.
  - «تسجيل تحويل التأمين» (للمحاسب بعد الاعتماد):
    - الطريقة: حساب أو هاتف.
    - الرقم المحوَّل إليه (يُعبّأ مسبقاً من طلب الضيف).
    - البنك (قائمة البنوك العمانية مع إمكانية الكتابة)، واسم صاحب الحساب، ورقم مرجع التحويل.
    - تاريخ ووقت التحويل بتوقيت مسقط (لا يقبل وقتاً في المستقبل).
    - إيصال التحويل إلزامي: صورة (تُضغط تلقائياً) أو PDF.
- **التنبيهات:**
  - لوحة المالك وجرس التنبيهات: «قرارات استرداد التأمين» و«تحويلات التأمين»، كل منها بحسب صلاحية صاحب الحساب.
  - نظرة العقار العامة: تنبيهان بالعدد.
- **المزامنة الحية:** الطلب أو القرار أو التحويل يظهر في الحسابات الأخرى وصفحة الضيف دون إعادة تحميل، عبر محفّزات `live_changes` القائمة.

### 4. الصلاحيات والخصوصية

| الإجراء                    | الصلاحية                                       | الأدوار                                                |
| -------------------------- | ---------------------------------------------- | ------------------------------------------------------ |
| اعتماد الاسترداد أو رفضه   | `stay.booking.manage` أو `stay.refund.approve` | مالك المنظمة، مدير المنظمة، مدير العقار، المدير المالي |
| تسجيل التحويل ورفع الإيصال | `payment.refund`                               | مالك المنظمة، المدير المالي                            |
| طلب الاسترداد              | رمز الحجز (`ref`) كباقي إجراءات الضيف          | الضيف                                                  |

- أرقام الحسابات تظهر كاملة لأصحاب الصلاحيات أعلاه فقط. وغيرهم يراها مخفية (`••••` + آخر 4 أرقام). والضيف يرى حسابه مخفياً كذلك.
- **إيصال التحويل:**
  - لا يُرسل مع قائمة الحجوزات.
  - يُفتح من مسار مستقل يتطلب جلسة حيّة وصلاحية القرار أو التحويل.
  - لا يُخزَّن في ذاكرة المتصفح المؤقتة (`no-store`).
  - لا يظهر للضيف.
- كل الاستعلامات مقيّدة بالمنظمة (`organization_id`)، وبالعقار عند المالك.

### 5. التخزين (دون ترحيل لقاعدة البيانات)

- **`stay_refunds`** (جدول قائم) يحمل الحالة:
  - `requested` ← `approved` ← `executed`، أو `rejected`.
  - `amount_minor`، و`approved_by_user_id` و`approved_at`، و`executed_at` (وقت التحويل).
  - `idempotency_key = 'deposit:<bookingId>'`.
- **`stay_booking_status_history`** يحمل تفاصيل كل حدث:
  - `to_status = 'deposit_refund'` و`reason = 'deposit_refund_<event>'`.
  - `metadata_json`: الحدث (`requested` أو `approved` أو `rejected` أو `paid`) مع الملاحظة، وبيانات الاستلام أو التحويل، والإيصال.
  - هذا السجل علامة فقط، ولا يغيّر حالة الحجز. القراءات التي تعتمد على السجل تفلتر بحالات الدخول والمغادرة فقط.
- عند التحويل أو الرفض ينتقل الحجز `checked_out ← closed`، مع سطر في السجل.
- كل حدث يُسجَّل أيضاً في `workflow_events` و`outbox_events` (`stay.deposit_refund.<event>`).
- قفل استشاري لكل حجز يمنع قرارين متزامنين.

### 6. رسائل الأخطاء

| الرمز                     | المعنى                                        |
| ------------------------- | --------------------------------------------- |
| `refund_not_open`         | الحجز لم يغادر بعد، أو أُغلق                  |
| `refund_no_deposit`       | لا يوجد مبلغ تأمين لهذا الحجز                 |
| `refund_already_decided`  | الطلب بُتّ فيه من قبل                         |
| `refund_not_approved`     | لا يُسجَّل تحويل قبل الاعتماد                 |
| `refund_note_required`    | الرفض يحتاج ملاحظة                            |
| `refund_account_invalid`  | رقم الحساب أو الهاتف غير صالح                 |
| `refund_receipt_required` | إيصال التحويل مطلوب (صورة أو PDF، حتى ~1.2MB) |

## التحقق

- **الفحوص:** فحص الأنواع ناجح، وESLint على الملفات الجديدة والمعدّلة دون أخطاء.
- **الاختبارات:**
  - 4 اختبارات جديدة: مرحلة الحجز، والتحقق من الحساب، والإخفاء، والخطوة الخامسة في الرحلة.
  - مع اختبارات التحية: 10 من 10 ناجحة.
  - الإخفاقات المعروفة سابقاً (`next-write-route-policy` و`proxy-canonical-host`) لا علاقة لها بهذا الإصدار.
- **قاعدة الإنتاج (قراءة فقط):**
  - أعمدة `stay_refunds` وقيودها (`amount > 0`، وقائمة الحالات) مطابقة.
  - لا قيد على `to_status` في سجل الحالة، و`metadata_json` افتراضيه `{}`.
  - الحجز ST-FE61E6C8: `checked_out`، والتأمين 80 ر.ع.، ولا طلبات استرداد بعد.
- **معاينة محلية** لحالات الضيف الخمس (قبل الطلب، وقيد المراجعة، ومعتمد، ومرفوض، ومُحوَّل)، وخلايا المالك ونماذج الاعتماد والتحويل.
- لم يُنشأ أي طلب استرداد حقيقي على الإنتاج للاختبار.

## ملاحظات

- **لا ترحيل لقاعدة البيانات:** الجدولان المستخدمان قائمان.
- **إيصال التحويل:** يُخزَّن داخل سجل الحالة كما في صور وثائق الاستلام (0.8.1). عند كثرة الإيصالات يُنقل إلى تخزين ملفات مستقل.
- **مسار طلب الضيف:** عام برمز الحجز، مثل الإلغاء وتغيير الموعد. لذلك يظهر في اختبار `next-write-route-policy` كبقية مسارات الضيف.
- **الخصم الجزئي:** يكون بتقليل المبلغ عند الاعتماد مع ذكر السبب في الملاحظة.
- **التالي المقترح:**
  - إشعار الضيف بالبريد أو واتساب عند القرار والتحويل.
  - ربط التحويل بقيد محاسبي في دفتر المالية.
