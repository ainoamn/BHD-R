## 1. النتيجة التنفيذية قبل التفاصيل

`bhd-om` ليس موقع عقارات بسيطاً، بل محاولة لجمع أربعة منتجات في منصة واحدة:

1. موقع عام للتسويق والعرض والحجز والمعاينة.
2. CRM ودفتر عناوين للأفراد والشركات والملاك والمستأجرين والمفوّضين.
3. نظام إدارة ممتلكات: عقارات، وحدات، حجوزات، عقود، صيانة، مهام وبوابات.
4. نظام مالي: دفعات، إيصالات، شيكات، محاسبة مزدوجة القيد، اشتراكات وتقارير.

المشكلة ليست فقر الفكرة؛ بالعكس، نطاق الأعمال غني. المشكلة أن المشروع الحالي يجمع **نظاماً حديثاً جزئياً** مع **نظام عقاري قديم مضمّن**، ولكل واحد حالات وبيانات ومحاسبة مختلفة. بعض الشاشات الحديثة تحفظ في PostgreSQL، وبعضها يحفظ JSON، وبعضها يكتب إلى `localStorage` ثم يحاول مزامنته إلى Legacy KV. لذلك ينبغي عند بناء BHD R نقل **السلوك التجاري الصحيح** لا طريقة التخزين الحالية.

الحكم الدقيق:

- رحلة الحجز والعقد تحتوي بالفعل على اعتماد محاسب، مستندات، شيكات، اعتماد إدارة، توقيع العميل، توقيع المالك، واعتماد نهائي.
- النظام القديم المضمّن يحتوي على صيانة ومهام ومحاسبة تشغيلية أغنى بكثير من واجهة الصيانة الحديثة.
- المحاماة ليست وحدة تشغيلية مكتملة في `bhd-om` الحديث؛ الموجود أساساً نصوص قانونية في العقود وصلاحيات/وعود منتج، لا إدارة قضايا متكاملة.
- عدة ضوابط مهمة موجودة في React فقط، ولا يفرضها الخادم. الشاشة قد تمنع الإجراء، لكن API قد يقبله إن أرسله مستخدم مصادق مباشرة.
- لا يمكن اعتبار النظام الحالي مصدراً مالياً أو تعاقدياً موحداً قبل إزالة الازدواج، فرض العزل والصلاحيات على الخادم، وتحويل المال إلى Decimal/وحدات صغرى.

## 2. كيف يتكوّن البرنامج فعلياً؟

### 2.1 الواجهة والتقنيات

| الطبقة                  | التقنية الفعلية                                               |
| ----------------------- | ------------------------------------------------------------- |
| تطبيق الويب وواجهات API | Next.js 16 App Router                                         |
| واجهة المستخدم          | React 19 + TypeScript                                         |
| التصميم                 | Tailwind CSS 4 وCSS مخصص                                      |
| الترجمة                 | `next-intl` للعربية والإنجليزية                               |
| قاعدة البيانات          | PostgreSQL عبر Prisma 7                                       |
| الجلسات والدخول         | NextAuth 4، Credentials، مزودات اختيارية، وربط BHD Identity   |
| التحقق                  | Zod في بعض المسارات، وتحقق يدوي في غيرها                      |
| الدفع                   | عدة موصلات مثل Stripe وThawani وPayPal وTelr وHyperPay وغيرها |
| التخزين                 | Vercel Blob، تخزين خاص قديم، وبيانات داخل DB/KV               |
| الكاش والحد من الطلبات  | Redis/Upstash اختيارياً                                       |
| الاختبارات              | Node test runner وPlaywright، بتغطية غير كافية للمخاطر        |

### 2.2 مصادر الحقيقة المتوازية

```text
الشاشات الحديثة
  ├─ جداول Prisma الطبيعية
  ├─ BookingStorage / ContractStorage بصيغة JSON
  ├─ AppSetting وLegacyAppKvStore
  └─ localStorage ومصفوفات TypeScript

النظام العقاري القديم المضمّن
  └─ سجلات KV للحجوزات والعقود والمحاسبة والصيانة والمهام
```

هذه ليست طبقات cache متطابقة، بل نماذج أعمال متوازية. أمثلة مهمة:

- إضافة عقار حديثة تدفع السجل إلى مصفوفة داخل `lib/data/properties.ts`، بينما API العقارات الإدارية يقرأ جدول `Property` في Prisma.
- الحجز والعقد الحديثان محفوظان كلقطة JSON في `BookingStorage` و`ContractStorage`.
- شاشة العمليات العقارية القديمة تقرأ `bhd_managed_units` و`bhd_saved_contracts_by_unit` من Legacy KV.
- الصيانة الحديثة في جدول `MaintenanceRequest` بسيطة، والصيانة القديمة في `bhd_maintenance_registry` غنية بالبنود والتكاليف والاعتمادات.
- المهام الحديثة في `TenantTask` محدودة، والمهام القديمة في `bhd_tasks_registry` تحتوي رسائل وتحويلات ومهام آلية.

هذا يفسر لماذا يمكن أن تبدو واجهة ما مكتملة، لكن النتيجة لا تظهر في شاشة أخرى أو على جهاز آخر.

## 3. هدف النظام التجاري

الرحلة التي يحاول البرنامج تنفيذها هي:

```text
مالك/شركة إدارة
  → تسجيل عقار ووحداته وصوره ومالكه
  → نشر الوحدات المتاحة
  → استقبال طلب معاينة أو حجز
  → تحصيل مبلغ الحجز وتأكيده محاسبياً
  → جمع هوية العميل ومستنداته وشيكاته
  → إنشاء عقد إيجار/بيع/استثمار
  → اعتماد الإدارة وتوقيع الطرفين
  → تحويل الوحدة إلى مؤجرة/مباعة وإخفائها من العرض
  → إنشاء الاستحقاقات والشيكات والقيود
  → تشغيل الصيانة والمهام والتنبيهات والتجديد أو الإلغاء
```

إذن المنتج المقصود هو مزيج من:

- Marketplace عقاري.
- CRM للأطراف والعلاقات.
- PMS لإدارة الممتلكات.
- Leasing/Contract Lifecycle.
- Finance & Accounting.
- Tenant/Owner Portals.
- Operations للصيانة والمهام والمتابعة.

## 4. المستخدمون والصلاحيات

### 4.1 الأدوار المخزنة

الأدوار الرئيسية في Prisma هي:

- `ADMIN`: مدير المنصة أو موظف إداري.
- `COMPANY`: حساب شركة.
- `ORG_MANAGER`: مدير مؤسسة.
- `OWNER`: مالك.
- `CLIENT`: عميل/مستأجر.

وتظهر أسماء إضافية في الشيفرة مثل `SUPER_ADMIN`, `ACCOUNTANT`, `LANDLORD`, `APPROVER`، لكنها ليست كلها أدوار قاعدة بيانات موحدة. توجد أيضاً صلاحيات إدارية تفصيلية مثل إدارة العقارات والحجوزات والمحاسبة والتقارير.

### 4.2 السلوك المقصود

| المستخدم        | ما يفترض أن يراه                         |
| --------------- | ---------------------------------------- |
| مدير المنصة     | كل المؤسسة أو كل المنصة بحسب النطاق      |
| مدير الشركة     | مؤسسته وعقاراتها وموظفيها فقط            |
| المالك          | عقاراته ووحداته وعقوده ومصروفاته فقط     |
| المستأجر        | حجوزاته وعقوده وفواتيره وصيانته فقط      |
| المحاسب/المعتمد | العمليات المالية المسموحة ضمن مؤسسته فقط |

### 4.3 ما يفرضه الكود فعلاً

الإنفاذ غير متساوٍ:

- `apiGuard` يقبل خيار `requiredPermissions` لكنه لا يفحص أسماء الصلاحيات فعلياً؛ يسمح للأدوار الإدارية المشابهة بصورة عامة.
- قائمة العقود وتعديل عقد يتطلبان المصادقة أساساً، لا قرار `tenant + resource + action` مركزياً.
- طبقة المحاسبة تحول `OWNER` إلى `APPROVER`، وكل دور آخر غير معروف تقريباً إلى `ACCOUNTANT`؛ لذلك قد يحصل عميل مصادق على قدرات محاسبية غير مقصودة.
- GET المحاسبة يعرض سجلات واسعة لأي جلسة لديها دور محاسبي مشتق، من دون عزل مؤسسة شامل.
- ملفات مستندات الحجز والشيكات تحفظ مصفوفات كاملة ويستطيع عدد واسع من الأدوار الكتابة إليها.

هذه نقطة يجب أن تكون بوابة المرحلة الأولى في BHD R: لا API خاص بلا Policy مصنفة واختبار رفض.

## 5. إضافة العقار والوحدات خطوة بخطوة

### 5.1 المسار الحديث الظاهر للمستخدم

صفحة إضافة العقار تستخدم معالجاً من أربع مراحل:

#### المرحلة 1 — البيانات الأساسية

- الاسم بالعربية والإنجليزية.
- رقم العقار والقطعة والرسم المساحي.
- الغرض: إيجار أو بيع أو استثمار.
- النوع: فيلا، شقة، مبنى، أرض، محل، معرض، مستودع وغيرها.
- تحديد هل العقار فردي أم متعدد الوحدات.

#### المرحلة 2 — الموقع والوحدات

- المحافظة، الولاية، المنطقة، القرية والشارع.
- العنوان الكامل وإحداثيات الخريطة.
- المساحة والغرف والحمامات والمواقف والتجهيزات.
- إذا كان متعدد الوحدات، يضيف المستخدم صفوف محلات ومعارض وشقق، ولكل وحدة رقم وسعر وتفاصيل.

#### المرحلة 3 — الصور والوسائط

- صورة رئيسية.
- معرض صور.
- بيانات العرض.

#### المرحلة 4 — المراجعة والحفظ

- مراجعة البيانات.
- حفظ كمسودة أو نشر.

### 5.2 ما يحدث تقنياً بعد الحفظ

الواجهة تستدعي `createProperty()` محلياً. هذه الدالة:

1. تحسب رقماً جديداً من طول/أكبر رقم في مصفوفة الواجهة.
2. تنشئ رقماً مثل `PRP-R-2025-xxxx`.
3. تدفع العقار إلى مصفوفة TypeScript داخل عملية المتصفح.
4. تحفظ تعديلات وحالات في `localStorage`/overrides.

لا يوجد في API قائمة العقارات POST مكافئ ينشئ هذا النموذج كاملاً في جدول Prisma. النتيجة أن العقار قد يظهر في نفس الجلسة ثم لا يكون سجلاً موحداً دائماً أو لا يظهر على جهاز آخر.

### 5.3 العقار متعدد الوحدات والعرض العام

الواجهة تفجّر العقار المتعدد إلى إعلانات منفصلة لكل وحدة. وتتحكم حالات الوحدة في الظهور. لكن السلوك الحالي يسمح أحياناً بعرض `RESERVED` إلى جانب `AVAILABLE`، وهذا يخالف القرار الجديد: الوحدة المحجوزة يجب أن تختفي فوراً من البحث العام.

التصميم الصحيح في BHD R:

```text
Property
  └─ Building (اختياري)
      └─ Unit (إلزامي دائماً)
          └─ Listing
```

- العقار الفردي ينشئ وحدة واحدة آلياً.
- لا ينشر الإعلان إلا إذا كان `published` والوحدة `available` ولا يوجد hold/reservation/lease/maintenance blocker.
- الصور الأصلية خاصة، والنسخ العامة WebP/AVIF مائية وممسوحة.
- الحفظ transaction واحدة ويدعم idempotency.

## 6. دفتر العناوين وإضافة الأفراد والشركات

دفتر العناوين هو CRM مصغّر، ويستعمل لربط:

- العملاء والمستأجرين.
- الملاك.
- الشركات.
- الموظفين والمفوّضين والممثلين.
- الموردين والجهات الأخرى.

### 6.1 الفرد

تخزن بيانات مثل الاسم العربي/الإنجليزي، الهاتف، البريد، الجنسية، الجنس، الرقم المدني أو الجواز، تواريخ الانتهاء، جهة العمل، الوظيفة والعنوان والمرفقات.

### 6.2 الشركة

تخزن الاسم التجاري، السجل التجاري، بيانات الضريبة، العنوان والحسابات، ثم ممثلي الشركة ومفوّضي التوقيع ووثائقهم.

### 6.3 الربط التلقائي

عند إنشاء حجز أو مستخدم يحاول النظام إيجاد جهة موجودة بالبريد أو الهاتف أو الهوية، ثم يربطها أو ينشئ جهة جديدة. توجد أدوات دمج التكرارات والاستيراد من CSV والمزامنة من الحجوزات.

### 6.4 الخلل

دفتر العناوين أيضاً هجين بين JSON مشفر، مخزن Legacy، ومرفقات. بعض APIs تعيد قائمة واسعة بعد تسجيل الدخول فقط. في النظام الجديد يجب فصل `Party`, `Person`, `Organization`, `PartyRole`, `Representative`, `Address`, `PartyIdentifier` مع تشفير حقول محدد وtenant policy.

## 7. رحلة المعاينة والحجز والدفع

### 7.1 اختيار الوحدة

الزائر يدخل صفحة العقار أو الوحدة، ثم يختار:

- طلب معاينة `VIEWING`.
- أو حجز `BOOKING`.

يدخل بيانات الفرد أو الشركة، الهاتف والبريد والهوية، ممثلي الشركة عند الحاجة، الوحدة، موعد المعاينة، السعر، الدفع والموافقة على الشروط.

### 7.2 إنشاء الحجز

الواجهة تنشئ معرفاً محلياً وتحدث حالتها، ثم ترسل POST إلى `/api/bookings`. الخادم:

1. يتحقق من المعرف والحمولة.
2. يولد رقم BKG ذرياً.
3. يحمل الحجوزات المخزنة ويفحص وجود حجز نشط مكرر.
4. يعمل upsert في `BookingStorage` مع JSON وحقول منزوعة التطبيع.
5. إذا كان الحجز مدفوعاً يحاول إنشاء إيصال محاسبي معلق.

فحص التكرار منفصل عن الحفظ، لذلك يستطيع طلبان متزامنان اجتياز الفحص قبل أن يكتب أي منهما. لا يوجد قيد قاعدة بيانات يعبّر عن «حجز نشط لنفس الوحدة والطرف».

### 7.3 حالات الحجز

الحالات الحديثة هي:

```text
PENDING → CONFIRMED → RENTED أو SOLD
    └──────────────→ CANCELLED
```

والنوع `BOOKING` أو `VIEWING`. من الأفضل في BHD R فصل المعاينة عن الحجز لأن المعاينة لا ينبغي أن تحمل حالات مالية وعقدية الحجز نفسها.

### 7.4 اعتماد المحاسب لمبلغ الحجز

إذا احتوى الحجز على دفع، يظهر في `/api/bookings/pending-confirmation`. المحاسب/المستخدم الإداري يفتح الحجز ويراجع المرجع والمبلغ والإيصال ثم يستدعي `/api/bookings/{id}/confirm-receipt`.

عند التأكيد يحاول النظام:

- وضع `accountantConfirmedAt`.
- تغيير الحجز إلى `CONFIRMED`.
- ربط رقم إيصال إن وجد.

هذه العلامة هي بوابة الخادم لإنشاء العقد. `POST /api/contracts` يرفض إن لم يجد `accountantConfirmedAt`.

لكن توجد مشكلات:

- مسار التأكيد يفحص «إداري» أكثر مما يفحص صلاحية محاسبية دقيقة.
- بعض منطق اعتماد الإيصال وترحيله موجود في دالة عميلة موازية، وليس في المعاملة الخادمية نفسها.
- إنشاء إيصال الحجز قد يفشل ويُلتقط الخطأ بينما يبقى الحجز محفوظاً.
- لا توجد معاملة واحدة تربط الدفع والحجز والإيصال والقيد.

### 7.5 إلغاء الحجز

- إن لم توجد روابط مالية، يمكن إلغاء/حذف الحجز مباشرة.
- إن وجد دفع، ينشأ طلب إلغاء ينتظر المحاسب ليسجل رد المبلغ أو الخصم أو الملاحظة.
- إذا كان الحجز مرتبطاً بعقد، يفترض أن ينتقل الإلغاء إلى دورة العقد لا حذف الحجز.
- عند الإلغاء تعاد الوحدة إلى متاحة، وعند `RENTED/SOLD` تختفي من العرض.

## 8. المستندات والشيكات قبل العقد

### 8.1 المستندات

ينشئ النظام قائمة متطلبات بحسب نوع العميل، مثل:

- البطاقة المدنية أو الجواز.
- السجل التجاري.
- بطاقات المفوضين.
- مستندات مالك حساب الشيك.
- ضمان دفع أو مستندات إضافية.

الحالات:

```text
PENDING → UPLOADED → APPROVED
                    └→ REJECTED → إعادة رفع
```

الإدارة تراجع كل مستند وتقبل أو ترفض مع سبب ثنائي اللغة. لا يسمح منطق الواجهة بالانتقال إلى اعتماد العقد قبل قبول كل المتطلبات الإلزامية.

### 8.2 الشيكات

يدخل العميل رقم الشيك، المبلغ، التاريخ، البنك، اسم ورقم الحساب، هوية مالك الحساب وصورة الشيك. يجب تعديل الشيك المرفوض قبل إعادة اعتماده، ولا ينبغي قبوله بلا صورة.

### 8.3 الخلل الأمني والوظيفي

- API إعدادات/بيانات المستندات يستطيع عدد كبير من الأدوار إرسال المصفوفة كاملة.
- GET لا يطبق دائماً نطاق الحجز/المستخدم/المؤسسة.
- بعض أسماء المعتمدين hard-coded مثل «المالك» أو «إدارة العقار» بدلاً من هوية الجلسة.
- لا توجد خدمة ملفات واحدة تفحص magic bytes والحجم والبرمجيات الخبيثة وتفرض ملكية الملف.

|       4 | إنشاء العقد                       | الإدارة          | الخادم يسمح بعد تأكيد المحاسب   | الحجز مرتبط ومؤكد                  | عقد `DRAFT`                        |
|       5 | الاعتماد المبدئي                  | الإدارة          | موظف الإدارة                    | اكتمال العقد والمستندات والشيكات   | `ADMIN_APPROVED`                   |
|       6 | توقيع العميل                      | رابط توقيع       | العميل/المستأجر/المشتري         | اعتماد الإدارة                     | `TENANT_APPROVED`                  |
|       7 | توقيع المالك                      | رابط توقيع       | المالك/البائع                   | توقيع العميل                       | `LANDLORD_APPROVED`                |
|       8 | الاعتماد النهائي                  | الإدارة          | مدير                            | وسائط توثيق الطرفين + كل المتطلبات | `APPROVED`, الحجز `RENTED/SOLD`    |
|       9 | استلام التأمين والشيكات في Legacy | العقد يولد طلبات | محاسب لديه `approve_accounting` | مراجعة المرفق واختيار بنك وملاحظة  | held/approved، دورة العقد `active` |
|      10 | صيانة عند وجود متأخرات            | الموظف           | مدير النظام                     | متأخرات شيكات إيجار                | `pending_approval → pending`       |
|      11 | مستند/قيد محاسبي حديث             | المحاسب          | `APPROVER/ADMIN`                | صلاحية اعتماد                      | `APPROVED`/posting                 |
|      12 | تغيير باقة يدوي                   | المستخدم/المدير  | ADMIN                           | طلب pending                        | approved/rejected                  |

المصفوفة تصف السلوك المقصود في الشاشات. الخادم لا يفرض كل الصفوف بهذه القوة، خصوصاً خطوات العقد والمستندات والشيكات.

## 10. العقود الحديثة خطوة بخطوة

### 10.1 إنشاء المسودة

العقد يدعم `RENT`, `SALE`, `INVESTMENT`، ويحمل بيانات الأطراف والعقار والتواريخ والإيجار/البيع والتأمين والرسوم والضريبة والعدادات والشيكات والجداول.

`POST /api/contracts` يتطلب:

- جلسة مصادق عليها.
- `id` و`bookingId`.
- وجود الحجز.
- تأكيد المحاسب للدفع.

ثم يحفظ العقد في `ContractStorage` ويكتب نسخة منه وحالته داخل `BookingStorage` للتوافق.

### 10.2 الاعتماد المبدئي للإدارة

في صفحة العقد تتحقق الواجهة من:

1. اكتمال حقول العقد الإلزامية.
2. قبول كل مستندات الحجز.
3. قبول كل الشيكات المطلوبة.

ثم تنقل العقد:

```text
DRAFT → ADMIN_APPROVED
```

وتسجل وقت واسم/رقم المعتمد إن توفر.

### 10.3 رابط توقيع العميل

الإدارة تنشئ رابطاً يحمل token. صفحة التوقيع تجمع:

- صورة سلفي.
- رسم/صورة توقيع.
- واجهة بطاقة الهوية.
- خلفية بطاقة الهوية.
- اسم الموقّع ومعلومات جهاز محدودة.

بعد رفعها بنجاح ينتقل الحجز/العقد:

```text
ADMIN_APPROVED → TENANT_APPROVED
```

### 10.4 توقيع المالك

بعد توقيع العميل ترسل الإدارة رابطاً للمالك. عند اكتمال الصور والتوقيع:

```text
TENANT_APPROVED → LANDLORD_APPROVED
```

### 10.5 الاعتماد النهائي

الواجهة تشترط وجود وسائط التوثيق الأربعة لكل طرف، وكل المستندات والشيكات. ثم تحول العقد إلى `APPROVED` وتحدث الحجز والوحدة إلى مؤجر/مباع.

### 10.6 المشكلات الحرجة في هذا المسار

1. شروط الاعتماد النهائي في React أساساً؛ PATCH العقد على الخادم يقبل patch واسعاً من أي مستخدم مصادق ولا يشغّل آلة حالات وصلاحيات مماثلة.
2. إنشاء رابط التوقيع يتطلب جلسة فقط، ولا يثبت أن المستخدم يملك الحجز أو صلاحية إدارة عقده.
3. token التوقيع يبحث بمسح حتى 5000 حجز، ويخزن داخل JSON، ولا يظهر انتهاء زمني أو hash مستقل.
4. صور الهوية والسلفي والتوقيع تحفظ Data URLs ضخمة داخل JSON الحجز، بدلاً من ملفات خاصة مشفرة وروابط قصيرة.
5. بعض مسارات التوقيع تستخدم `JSON.parse(row.data)` مباشرة، بينما بقية النظام يدعم serialization/encryption؛ وهذا قد يفشل عند تشفير السجل.
6. تحديث `ContractStorage` و`BookingStorage` عمليتان، وليستا معاملة واحدة بversion/optimistic lock.
7. تحويل الوحدة إلى مؤجرة يبدأ من كود العميل ويستعمل مزامنة fire-and-forget؛ قد ينجح العقد وتفشل حالة الوحدة أو العكس.

في BHD R يجب أن تكون كل transition أمراً خادمياً مستقلاً مثل `submit`, `admin-approve`, `sign`, `finalize`, `cancel`، وليس PATCH حراً للحالة.

## 11. دورة العقد القديمة المضمّنة واعتماد الحسابات

النظام القديم لا يستخدم حالات `DRAFT/ADMIN_APPROVED` فقط، بل يحسب جاهزية تشغيلية للعقد:

```text
active_pending
  → active_docs_pending
  → active_accounting_pending
  → active
```

### 11.1 الحفظ والتفعيل

الموظف يختار مبنى ووحدة، ثم يملأ أو يجدد العقد. عند التفعيل يتحقق الخادم من رقم الاتفاقية، المستأجر، تاريخ البداية والنهاية، والإيجار الشهري. بعد ذلك:

1. يدمج البيانات الجديدة مع العقد السابق إن كان تجديداً.
2. يحسب حالة الدورة قبل المزامنة.
3. يولد سجلات التأمين والشيكات والاستحقاقات في سجل المحاسبة القديم.
4. يعيد حساب الحالة.
5. يحفظ العقد في `bhd_saved_contracts_by_unit`.
6. يحدث `bhd_managed_units`.
7. يؤرشف النسخة السابقة في التجديد.
8. يزيل المسودة.

### 11.2 معنى الحالات

- `active_pending`: بيانات مالية إضافية ناقصة، مثل جدول دفعات أو مرفق تأمين.
- `active_docs_pending`: الرقم البلدي أو حزمة مستندات العقار/العقد ناقصة.
- `active_accounting_pending`: البيانات والمستندات موجودة، لكن استلام التأمين أو الشيكات ينتظر المحاسب.
- `active`: استوفيت المتطلبات المحاسبية والتوثيقية.

### 11.3 كيف يعتمد المحاسب؟

عند مزامنة العقد تُنشأ عناصر `pending_receipt` للتأمين والشيكات. المحاسب:

1. يفتح «طلبات الاعتماد».
2. يعاين المرفق وصورة الشيك.
3. يطابق الرقم والمبلغ والتاريخ والعقد.
4. يختار الحساب البنكي الذي سيستلم المبلغ/الشيك.
5. يكتب ملاحظة اعتماد إلزامية.
6. يعتمد أو يرفض.

عند اعتماد التأمين:

- ينشأ رقم سند إن لم يوجد.
- تتغير الحالة إلى `held`.
- يسجل `receiptApprovedAt`, اسم المعتمد، البنك والملاحظة.
- ينعكس رقم السند إلى العقد والوحدات المرتبطة.

وعند اعتماد الشيك تسجل البيانات المماثلة. يمكن اعتماد مجموعة شيكات بعد مراجعة كل واحد. الشيك غير المحدد يبقى معلقاً، والمرفوض يصبح `receipt_rejected` ويمنع اكتمال دورة العقد.

هذا منطق تجاري مفيد يجب نقله، لكن تنفيذه القديم يعتمد على سجلات JSON في المتصفح/KV وصلاحيات واجهة، لا جداول ومعاملات محاسبية موثوقة.

## 12. المحاسبة الحديثة

### 12.1 الوحدات الموجودة

- دليل الحسابات.
- قيود يومية وأسطر مدين ودائن.
- فواتير، إيصالات، دفعات، عروض، أوامر شراء وإشعارات دائنة/مدينة.
- فترات مالية وقفل.
- تقارير ميزان مراجعة ودخل وميزانية وتدفق نقدي وضريبة وأعمار ذمم وتسوية بنك.
- سجل تدقيق.

### 12.2 إنشاء مستند

`POST /api/accounting/documents` يتطلب `DOCUMENT_CREATE`، ثم ينشئ المستند. الحالة الافتراضية في المسار هي `APPROVED`، وإذا كان Approved/Paid يولد قيداً مباشرة.

### 12.3 اعتماد مستند

`POST /api/accounting/documents/{id}/approve` يتطلب `JOURNAL_APPROVE`، يغير المستند إلى `APPROVED` ثم ينشئ القيد ويربطه بالمستند.

### 12.4 القيد

عند إنشاء القيد:

1. يتحقق أن الفترة غير مقفلة.
2. يولد رقماً متسلسلاً ذرياً من `SerialCounter`.
3. يجمع المدين والدائن ويقبل فرقاً لا يتجاوز `0.01`.
4. ينشئ القيد والأسطر.
5. يحدث رصيد كل حساب سطراً بعد سطر.
6. يكتب سجل تدقيق.

### 12.5 مشكلات تمنع الاعتماد المالي الحقيقي

- المال `Float` وJavaScript `number`، وليس Decimal أو bigint minor units.
- إنشاء القيد وتحديث أرصدة الحسابات وكتابة audit ليست ظاهرة كمعاملة ذرية واحدة؛ فشل منتصف الطريق قد يترك أرصدة جزئية.
- الأرصدة تتحدث عند إنشاء القيد حتى لو كانت حالته DRAFT/PENDING، بينما اعتماد القيد لاحقاً يغير الحالة فقط.
- إلغاء القيد يغير الحالة إلى `CANCELLED` ولا ينشئ قيداً عكسياً ولا يعيد الأرصدة.
- اعتماد المستند ليس idempotent transaction محمية؛ طلبان متزامنان قد ينشئان قيدين قبل ربط `journalEntryId`.
- لا tenant key شامل في معظم الجداول المالية.
- mapping الأدوار المحاسبية يمنح صلاحيات زائدة.
- `createdBy` يساوي `system` في مواضع بدلاً من هوية الفاعل.

الأرقام المتسلسلة المحاسبية نفسها تستعمل upsert/increment ذرياً، وهو جزء جيد يمكن الحفاظ على فكرته.

## 13. نظام الصيانة

يوجد نظامان مختلفان.

### 13.1 الصيانة الحديثة

المستأجر أو المالك يدخل `/admin/my-maintenance` ثم:

1. يختار/يرسل معرف العقار واسم العرض.
2. يكتب الوصف بالعربية، والإنجليزية اختيارية.
3. يحدد الأولوية وبيانات التواصل.
4. ينشئ `MaintenanceRequest` بحالة `OPEN`.

الإدارة ترى كل الطلبات وتستطيع تعديل:

```text
OPEN → IN_PROGRESS → COMPLETED
  └───────────────→ CANCELLED
```

وعند تغير الحالة ينشأ Notification لصاحب الطلب.

قيود هذا النظام:

- لا يثبت أن العقار المرسل يخص المستأجر أو عقده.
- لا `organizationId` أو وحدة/عقد بعلاقة إلزامية.
- لا فني أو مورد أو عرض سعر أو SLA أو موعد أو مرفقات أو تكلفة أو موافقة مالك.
- كل الأدوار الإدارية المسموحة ترى كل الطلبات بلا نطاق مؤسسة ظاهر.

### 13.2 الصيانة القديمة الغنية

النظام القديم يحتوي على:

- كتالوج بنود: تكييف، كهرباء، سباكة وعام.
- مواد، أجور، كمية وسعر يدوي.
- موظف مسؤول على مستوى البند/الطلب.
- حالات `pending_approval`, `pending`, `in_progress`, `completed`, `cancelled`.
- سجل حركات وملاحظات ومرفقات إكمال.
- ربط بمهمة متابعة.
- ربط بالمحاسبة وإصدار فاتورة صيانة.

#### إنشاء الطلب

1. الموظف يختار المبنى والوحدة.
2. يضيف بند صيانة واحداً على الأقل.
3. النظام يجلب المستأجر والعقد والمتأخرات.
4. يحسب تكلفة المواد والأجور.
5. إن كان على المستأجر شيكات إيجار متأخرة يصبح الطلب `pending_approval` ولا يظهر للفني.
6. إن لم توجد متأخرات يصبح `pending`.
7. يسجل المنشئ والوقت والحدث الأول.

#### اعتماد الإدارة

مدير النظام فقط يوافق على طلب `pending_approval`. بعد الموافقة يصبح `pending` ويظهر للموظف المسؤول.

#### التنفيذ

- بدء التنفيذ يتطلب ملاحظة، ويحوّل الحالة إلى `in_progress`.
- ينشأ تلقائياً Task لفريق الصيانة.
- الإكمال يتطلب ملاحظة، ويمكن جعل صور/فيديو الحل إلزامية.
- يحفظ `completedAt`, `completedBy`, التكلفة النهائية والمرفقات.
- يستطيع الفني طلب إعادة البلاغ، ويستطيع المدير إعادته أو تحويل طلب مكتمل للمتابعة.

#### الربط بالحسابات

بعد الإكمال يستطيع المحاسب:

1. تعديل المبلغ النهائي مع حدث تدقيق.
2. ربط الطلب بالمحاسبة.
3. إنشاء بند دخل/مطالبة على الوحدة.
4. إنشاء فاتورة صيانة واعتمادها.
5. طباعتها أو مشاركتها عبر واتساب/البريد.

يمكن فك الربط في النظام القديم بحذف البند والفاتورة، وهذا لا يناسب دفتر أستاذ غير قابل للمحو؛ النظام الجديد يجب أن يستخدم إلغاء/قيداً عكسياً.

### 13.3 مسار الصيانة المطلوب في BHD R

```text
REPORTED
  → TRIAGED
  → QUOTE_REQUESTED
  → APPROVAL_PENDING
  → APPROVED
  → SCHEDULED
  → IN_PROGRESS
  → WORK_COMPLETED
  → VERIFIED
  → INVOICED
  → CLOSED

أي مرحلة مناسبة → CANCELLED / REJECTED / REOPENED
```

مع SLA، مورد، أمر عمل، عرض سعر، موافقة مالك حسب حد مالي، صور قبل/بعد، ضمان عمل، تكلفة على المالك أو المستأجر، وقيد/فاتورة غير قابلة للتكرار.

## 14. نظام المهام

### 14.1 المهام الحديثة

جدول `TenantTask` يدعم النوع، العنوان، الوصف، المسند، المنشئ، الحالة، الموعد والسجل المرتبط. API الحالي يسمح للمستخدم برؤية المهام التي أنشأها أو أسندت إليه وتغيير حالتها.

المشكلة أن API لا يحتوي POST واضحاً لإنشاء مهمة، ولا workflow اعتماد أو تعليقات أو مرفقات أو انتقالات مفروضة. بل يسمح للمسند أو المنشئ بوضع أي حالة من القائمة مباشرة.

### 14.2 المهام القديمة

النظام القديم أغنى ويحتوي:

- أرقام `TSK-YYYY-NNNN`.
- فرق: الإدارة، الصيانة، المحاسبة.
- أولويات ومواعيد.
- مسؤولون ومطلعون Watchers.
- رسائل وردود ومرفقات ومتابعات.
- تحويل كامل للمهمة مع إبقاء السابق مطلعاً.
- ربط بعقار أو وحدة أو شيكات أو صيانة أو مهمة أم.
- سجل أحداث وتنبيهات للمشاركين.

### 14.3 المهام الآلية

ينشئ النظام القديم مهاماً تلقائية من:

- عقد قريب الانتهاء.
- بطاقة/جواز/سجل تجاري قريب الانتهاء.
- شيك حان إيداعه.
- شيك/مستأجر متأخر بعد عدد أيام مضبوط.
- بدء أو إعادة فتح صيانة.

يستعمل `sourceKey` لمنع إنشاء المهمة التلقائية نفسها مرة أخرى في السجل المحلي. ثم يلغي المهمة تلقائياً إذا زال السبب.

هذه قواعد ممتازة للمنتج الجديد، لكن يجب تنفيذها في Worker/Outbox وجداول طبيعية مع unique constraint، لا مزامنة خفية تعمل عند فتح المتصفح.

## 15. بوابات المستأجر والمالك والإدارة

### 15.1 المستأجر

يعرض الإصدار الحديث:

- العقود المرتبطة به.
- المبالغ المستحقة والمتأخرة.
- التنبيهات والمهام.
- الصيانة.
- التقييم المبني على قواعد.
- تقويم الاستحقاقات.
- التوقيع والدفع.

بعد التأجير توجد فكرة إنشاء حساب تلقائي للمستأجر، لكن النظام القديم يعرض/يرجع كلمة مرور مؤقتة في بعض التدفقات. الصحيح في BHD R هو إنشاء هوية مرتبطة بـBHD Identity وإرسال رابط تفعيل أحادي الاستخدام، ثم إبطال الرمز بعد الاستعمال.

### 15.2 المالك

تعرض البوابة عقارات `ownerId` والعقود وبعض المصروفات وتقييمات المستأجرين. يوجد KPI باسم الدخل لكنه في موضع يساوي عدد العقود لا مجموع الإيراد، ولذلك لا يجوز اعتباره تقريراً مالياً.

### 15.3 الإدارة

لوحة الإدارة تجمع الحجوزات والمستخدمين والمشاريع والاشتراكات والصيانة والرسائل والعقود، إضافة إلى شاشة النظام القديم للعقود والوحدات والمحاسبة والصيانة والمهام.

في BHD R يجب ألا تكون اللوحات مجرد إخفاء قوائم؛ كل لوحة تقرأ Projection محددة بصلاحيات خادمية:

- Platform: مؤسسات، باقات، سياسات، دعم ومراقبة.
- Owner: محفظة المالك، الدخل، المصروفات، الاعتمادات والممثلون.
- Developer: المشاريع والمخزون والمبيعات والتحصيل.
- Tenant: عقده، فواتيره، طلباته وصيانته فقط.

## 16. الأنظمة الأخرى

### 16.1 الإشعارات

توجد Notifications في Prisma مع `dedupeKey`. تنشأ من حالات الحجوزات والعقود والصيانة، ويمكن قراءتها وتعليمها. لكن مزامنة بعض الإشعارات تحدث أثناء GET وتقرأ حتى مئات الحجوزات، وهذا side effect ومشكلة توسع. الصحيح Outbox → Worker → قنوات Email/SMS/WhatsApp/In-app.

### 16.2 الاشتراكات والباقات

توجد Basic/Standard/Premium/Enterprise، وحدود وميزات JSON، وتغيير باقة واعتماد مدير. لكن مسار `change-with-payment` يثق في مبلغ دفع قادم من جسم طلب العميل، وينشئ إيصالاً وقيداً ويطبق الترقية من دون إثبات capture من بوابة دفع موثقة. هذا خلل P0.

### 16.3 التقارير

- تقارير المحاسبة الحقيقية تحسب من القيود.
- Custom CSV يعمل جزئياً للحجوزات والجهات والصيانة والرسائل.
- Advanced Reports يحاكي إنشاء PDF وحجماً عشوائياً ورابطاً محلياً.
- Analytics تستعمل بيانات مولدة في مواضع.

يجب ألا يسمى تقريراً إلا إذا كان له query موثق، tenant scope، تاريخ بيانات، ملف حقيقي، واختبار reconciliation.

### 16.4 المحتوى وSEO

يوجد محتوى موقع وإعلانات وقوالب وشروط حجز وإعدادات في `AppSetting`. توجد sitemap وrobots وبيانات منظمة أولية. لكن المحتوى والعقارات العامة ما زالت تمزج الثابت بالديناميكي، ولا توجد canonical/hreflang وSEO لكل listing بصورة موحدة.

### 16.5 الأرشيف والنسخ

يوجد `ArchiveRecord` وRestore Log وسياسات وأعمال cron. لكن restore في بعض المواضع يسجل العملية ولا يعيد الكيان فعلياً. كما أن النسخ/التصفير لا تعادل PITR واختبار استعادة قاعدة حقيقية.

### 16.6 التشفير والأمن

يوجد تشفير وتدقيق وTOTP وAPI keys ومحاولات CSP. لكن التصميم الحالي يحتاج فصل مفاتيح لكل غرض، `kid/version`, تدوير مع dual-read/new-write، backfill قابل للاستئناف، redaction عميق للسجلات، CSRF شامل، وتقييد الملفات والروابط العامة وSSRF.

### 16.7 المحاماة

لا يوجد في التطبيق الحديث aggregate كامل للقضايا والمحامين والجلسات والأحكام. الموجود:

- نصوص وشروط قانونية داخل العقود.
- صلاحيات `LEGAL_VIEW/LEGAL_MANAGE` في مصفوفة الباقات.
- إشارات تسويقية إلى الفريق القانوني.

لذلك وحدة المحاماة في BHD R يجب أن تبنى كمنتج جديد: `LegalCase`, `Notice`, `Hearing`, `Judgment`, `Enforcement`, `Settlement`, `ClaimAmount`, `Evidence`, `LegalTask`, مع سرية أعلى وlegal hold.

## 18. المشكلات مرتبة حسب الأولوية

### P0 — تمنع الاعتماد الإنتاجي

1. تعديل حالة العقد من API بلا Policy مورد وآلة حالات مركزية.
2. عزل الشركات غير شامل، وقراءات واسعة للعقود والمحاسبة ودفتر العناوين.
3. mapping الأدوار المحاسبية يمنح CLIENT أحياناً دور ACCOUNTANT وOWNER دور APPROVER.
4. ترقية الاشتراك تثق في `payment.amount` من العميل ولا تثبت دفعاً فعلياً.
5. المال Float، والإلغاء المحاسبي لا يعكس الأرصدة، وإنشاء القيود قد يغير الأرصدة قبل posting.
6. اعتماد مستند مالي قد يتكرر تحت التزامن.
7. webhook/idempotency غير موحدين.
8. أسرار/PII قد تدخل audit/logs، والطباعة المبنية بـHTML تعرض XSS.
9. روابط عامة للحجز/الفاتورة/العقد تكشف أكثر من DTO أدنى وتحتاج token منتهياً ومجزأً.
10. إنشاء العقار الحديث ليس حفظاً موحداً دائماً.

### P1 — مخاطر تشغيل وبيانات كبيرة

1. أربعة مصادر حقيقة ومزامنة best-effort.
2. مستندات الهوية والتوقيع Data URLs داخل JSON.
3. final approval للعقد يعتمد على الواجهة.
4. مهام وصيانة حديثتان أبسط بكثير من السلوك القديم.
5. لا توجد وحدة محاماة فعلية.
6. التقارير والتحليلات المتقدمة محاكاة جزئية.
7. لا عزل tenant/RLS شامل.
8. بعض APIs تفك JSON خاماً ولا تدعم النسخة المشفرة.
9. البناء يشغّل migrations، ما يربط artifact build بتغيير قاعدة البيانات.
10. CSP يسمح `unsafe-inline` وتوجد سطوح `document.write` و`dangerouslySetInnerHTML`.

### P2 — أداء وجودة وقابلية صيانة

1. مسح آلاف صفوف JSON للعثور على token أو عقد أو حجز.
2. صفحات وخدمات ضخمة ومكررة.
3. side effects داخل GET.
4. localStorage كمصدر أعمال.
5. حسابات وتقارير في المتصفح.
6. صور وملفات بلا pipeline واحد.
7. اختبارات غير كافية لحالات السباق والعزل والتوقيع والإلغاء.

## 19. السلوك الذي يجب أن يثبته BHD R الجديد

لا يكتفي النظام الجديد بوجود شاشة. كل رحلة يجب أن تثبت على API وDB واختبارات:

1. إنشاء عقار فردي ينتج Property + Unit واحدة + Ownership داخل transaction.
2. إنشاء متعدد ينتج وحدات مستقلة ولا يعتمد على index مثل `apartment-1`.
3. الوحدة المحجوزة/المؤجرة/المباعة/تحت صيانة حاجبة تختفي فوراً من البحث.
4. طلب معاينة مستقل عن Reservation.
5. منع حجزين نشطين متزامنين بقيد DB وقفل/transaction.
6. الدفع لا يثبت إلا من webhook موقع وحدث فريد، وكل retries تعطي نتيجة واحدة.
7. العقد لا ينشأ قبل بوابة الحسابات والمتطلبات.
8. كل اعتماد `ApprovalRequest/Decision` به طالب، معتمد، سبب، وقت، version، tenant وresource.
9. التوقيع مربوط بـContractVersion وPDF hash ثابت، وtoken مجزأ ومنتهٍ وقابل للإلغاء.
10. التفعيل يحدث العقد والوحدة والحجز والاستحقاقات وoutbox في transaction واحدة.
11. القيد لا يؤثر في الحسابات قبل posting، ولا يعدل بعده؛ الإلغاء بقيد عكسي.
12. الصيانة تربط العقد والوحدة والمورد والتكلفة والاعتماد والفاتورة.
13. المهام تنشأ من events في worker بمفتاح unique ولا تعتمد على فتح شاشة.
14. القضايا القانونية وحدة مستقلة بسرية وlegal hold.
15. كل تقرير من بيانات حقيقية وله تعريف KPI وdrill-down ونطاق مؤسسة.
16. Tenant A لا يستطيع قراءة أو تعديل أو تنزيل أي مورد لـTenant B حتى بمعرف صحيح.

## 21. الخلاصة

النظام السابق ليس «بدائياً» من ناحية فهم الأعمال؛ داخله تفاصيل عملية كثيرة جداً. لكنه بدائي وخطير في **طريقة توحيد هذه التفاصيل**: منطق في المتصفح، JSON/KV، APIs واسعة، ونظامان متوازيان. لذلك بناء BHD R الصحيح لا يعني رسم شاشات أكثر، بل تحويل كل رحلة أعلاه إلى:

- نموذج بيانات واحد.
- صلاحية خادمية واحدة.
- آلة حالات واحدة.
- معاملة مالية صحيحة.
- سجل تدقيق منقح.
- أحداث خلفية قابلة للإعادة بلا تكرار.
- واجهة عمانية احترافية لا تعرض إلا ما يسمح به الخادم.
- اختبارات قبول تمنع الانتقال بين مراحل البناء قبل إثبات المرحلة السابقة.
